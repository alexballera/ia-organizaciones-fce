 ## Temas tratados

 ### Tema 1: RAG (Retrieval-Augmented Generation)

 **RAG (Retrieval-Augmented Generation), o generación aumentada por recuperación,** es una técnica que combina la búsqueda de información relevante con la generación de texto mediante un modelo de inteligencia artificial. Antes de elaborar una respuesta, el sistema recupera información desde fuentes externas y se la proporciona al modelo como contexto.

 RAG permite que un modelo utilice documentos institucionales, bases de datos, manuales o información actualizada sin necesidad de volver a entrenar sus parámetros cada vez que cambia el contenido.

 #### Cómo funciona, de forma simplificada

 El proceso puede resumirse en cuatro etapas:

 1. **Preparación de las fuentes:** los documentos se recopilan, limpian y dividen en fragmentos manejables.
 2. **Indexación:** cada fragmento se transforma en una representación numérica llamada *embedding* y se almacena en un índice, generalmente una base de datos vectorial.
 3. **Recuperación:** cuando una persona realiza una consulta, el sistema transforma la pregunta en un embedding y busca los fragmentos más relacionados.
 4. **Generación aumentada:** los fragmentos recuperados se incorporan al prompt. El modelo utiliza ese contexto para redactar una respuesta, idealmente indicando las fuentes utilizadas.

 Por ejemplo, ante la pregunta `¿Cuántos días de licencia corresponden según el reglamento interno?`, el sistema puede recuperar el apartado pertinente del reglamento vigente y utilizarlo para construir la respuesta. El modelo no depende únicamente de lo aprendido durante su entrenamiento general.

 #### Componentes principales

 - **Fuentes de conocimiento:** documentos, páginas, bases de datos o sistemas internos autorizados.
 - **Procesamiento de documentos:** tareas de limpieza, división en fragmentos y extracción de metadatos.
 - **Embeddings:** representaciones numéricas que permiten comparar la similitud semántica entre una consulta y los fragmentos almacenados.
 - **Índice o base de datos vectorial:** sistema que permite encontrar rápidamente los fragmentos más relevantes.
 - **Recuperador:** componente que selecciona el contexto que se enviará al modelo.
 - **Modelo generativo:** produce una respuesta utilizando la consulta y la información recuperada.
 - **Citas y controles:** mecanismos para indicar las fuentes y verificar la respuesta antes de utilizarla.

 #### Ejemplo de funcionamiento

 Una organización dispone de mil documentos sobre procedimientos administrativos. Una persona consulta: `¿Qué comprobantes necesito para solicitar el reintegro de una capacitación?`.

 1. El sistema convierte la consulta en un embedding.
 2. Busca en el índice los fragmentos más similares.
 3. Recupera el apartado del procedimiento de reintegros y sus requisitos.
 4. Envía esos fragmentos al modelo junto con la pregunta.
 5. El modelo responde con los comprobantes requeridos y muestra el documento de referencia.

 #### Ventajas de RAG

 - **Información actualizada:** permite consultar contenidos que cambian después del entrenamiento del modelo.
 - **Menor necesidad de fine-tuning:** para incorporar nuevos documentos normalmente basta con actualizar el índice.
 - **Trazabilidad:** facilita vincular la respuesta con las fuentes recuperadas.
 - **Adaptación al dominio:** permite utilizar vocabulario y conocimiento específico de una organización.
 - **Control de acceso:** puede recuperar únicamente documentos que la persona usuaria tiene autorización para consultar.

 #### Diferencia entre RAG y fine-tuning

 El **fine-tuning** modifica los parámetros del modelo mediante un entrenamiento adicional para adaptar su comportamiento a una tarea o estilo. En cambio, **RAG** conserva el modelo y le proporciona información externa en el momento de responder.

 Por ejemplo, el fine-tuning puede enseñar a un modelo a clasificar consultas con el formato institucional de una empresa. RAG puede permitirle consultar el reglamento vigente para responder una pregunta sobre requisitos. Ambas técnicas pueden utilizarse juntas, pero cumplen funciones diferentes.

 #### Límites importantes

 RAG no garantiza por sí solo que una respuesta sea correcta. Si la fuente contiene errores, está desactualizada o no fue recuperada, el modelo puede responder de manera incorrecta. También puede seleccionar fragmentos irrelevantes, interpretar mal el contexto o generar información que no aparece en los documentos.

 Por eso es necesario mantener las fuentes actualizadas, definir criterios de fragmentación, evaluar la calidad de la recuperación, controlar permisos y solicitar que el modelo indique cuando no encuentra información suficiente. En decisiones de alto impacto debe existir revisión humana.

 #### Ejemplos de aplicación

 - **Atención interna:** responder consultas sobre políticas, licencias, beneficios y procedimientos.
 - **Soporte técnico:** recuperar manuales y guías para orientar la resolución de incidentes.
 - **Análisis normativo:** buscar artículos relevantes de reglamentos o contratos.
 - **Gestión del conocimiento:** consultar informes, actas y documentación histórica de la organización.
 - **Educación:** responder preguntas utilizando apuntes y bibliografía autorizada.

 #### Ejemplo en una organización

 Un banco puede implementar un asistente RAG conectado a sus manuales de productos y procedimientos internos. Cuando un empleado consulta cómo gestionar un reclamo, el sistema recupera el procedimiento vigente y genera una guía con los pasos correspondientes y enlaces a las fuentes.

 El asistente no debería modificar cuentas, aprobar excepciones ni comunicar decisiones al cliente sin controles adicionales. Las herramientas y permisos deben limitarse a la consulta, y las acciones sensibles deben requerir validación del área responsable.

### Tema 2: Benchmarks para agentes de IA: SWE-bench, Terminal-Bench y horizonte METR

Un **benchmark** es una evaluación estandarizada que permite comparar el desempeño de distintos modelos o agentes frente a un conjunto definido de tareas. En el caso de los agentes de programación, no alcanza con medir si el modelo responde correctamente una pregunta: también interesa saber si puede utilizar herramientas, ejecutar comandos, modificar archivos, superar pruebas y completar una tarea de principio a fin.

#### SWE-bench

**SWE-bench** evalúa la capacidad de un sistema para resolver problemas reales de ingeniería de software. Sus tareas se basan en issues de repositorios públicos: el agente recibe una descripción del problema, accede al código y debe proponer cambios que solucionen el issue sin romper el comportamiento existente.

La evaluación suele verificar si el parche generado resuelve las pruebas asociadas al problema. Por eso mide capacidades como:

- Comprender una base de código existente.
- Localizar los archivos y funciones relevantes.
- Formular una hipótesis sobre la causa del problema.
- Editar el código y ejecutar pruebas.
- Corregir errores derivados de la primera solución.

El resultado suele expresarse como el porcentaje de instancias resueltas. Las variantes, como SWE-bench Lite o Verified, utilizan subconjuntos o procedimientos de validación diferentes; por eso los resultados solo deben compararse cuando coinciden la versión, el entorno y la metodología.

#### Terminal-Bench

**Terminal-Bench** evalúa agentes que trabajan mediante una terminal en un entorno computacional. Las tareas pueden requerir instalar dependencias, ejecutar comandos, manipular archivos, configurar servicios, procesar datos o resolver problemas técnicos con varias etapas.

A diferencia de una prueba de respuesta textual, el agente debe interactuar con un entorno real o simulado. Esto permite evaluar si puede:

- Elegir y encadenar comandos adecuados.
- Leer e interpretar la salida de la terminal.
- Diagnosticar errores de ejecución.
- Trabajar con archivos, programas y dependencias.
- Alcanzar un estado final verificable.

El entorno de evaluación debe estar aislado y controlado. Ejecutar comandos con permisos excesivos, conectividad irrestricta o acceso a datos reales podría provocar daños o invalidar la medición.

#### Horizonte de tareas de METR

METR propone medir el **horizonte de tareas** (*task horizon*) de un agente: la duración de una tarea realizada por una persona experta que el agente puede completar con una probabilidad determinada, por ejemplo, el 50 %. La duración se refiere al tiempo humano estimado para realizar la tarea, no necesariamente al tiempo que tarda el agente en ejecutarla.

Por ejemplo, si un agente resuelve correctamente la mitad de las tareas que a una persona experta le llevan aproximadamente una hora, se puede decir que su horizonte de tareas para ese nivel de éxito es cercano a una hora. Esta medida busca evaluar la capacidad de encadenar acciones durante períodos cada vez más largos.

El horizonte no significa que el agente pueda realizar de forma confiable cualquier tarea de esa duración. Depende del conjunto de tareas, del umbral de éxito, de las herramientas disponibles, del entorno y de la forma en que se mide el tiempo humano.

#### Comparación entre los benchmarks

| Evaluación | Qué mide principalmente | Tipo de entorno | Resultado habitual |
| --- | --- | --- | --- |
| SWE-bench | Resolución de issues reales de software | Repositorios y pruebas automatizadas | Porcentaje de issues resueltos |
| Terminal-Bench | Ejecución de tareas técnicas mediante terminal | Entorno computacional controlado | Porcentaje de tareas completadas |
| Horizonte METR | Longitud de las tareas que un agente completa con una probabilidad dada | Conjunto de tareas con duración humana estimada | Duración del horizonte para un nivel de éxito |

Los tres enfoques son complementarios. SWE-bench se concentra en mantenimiento de software, Terminal-Bench en interacción operativa con entornos computacionales y METR en la longitud o complejidad temporal de las tareas. Un agente puede obtener un buen resultado en uno y tener dificultades en otro.

#### Ejemplo de evaluación

Supongamos que se quiere comparar dos agentes de programación para una organización. SWE-bench puede mostrar cuál resuelve mejor errores reales en un repositorio. Terminal-Bench puede evaluar cuál configura correctamente un entorno y ejecuta las herramientas necesarias. El análisis de METR puede ayudar a estimar cuánto tiempo de trabajo encadenado puede realizar cada agente antes de requerir supervisión.

No sería suficiente observar únicamente el porcentaje final. También conviene registrar el costo, el tiempo de ejecución, la cantidad de intentos, los errores, el uso de herramientas y la necesidad de intervención humana.

#### Límites de los benchmarks

- Un resultado alto en un benchmark no garantiza desempeño general en una organización.
- La contaminación de datos o la familiaridad previa con las tareas puede inflar los resultados.
- Cambiar el modelo, las herramientas, el prompt o el entorno puede cambiar significativamente la medición.
- Las pruebas automatizadas pueden no detectar problemas de seguridad, mantenibilidad o calidad organizacional.
- Un agente puede completar la tarea, pero utilizar demasiados recursos o requerir una supervisión que elimine el beneficio práctico.

Por eso, los benchmarks deben combinarse con pruebas internas, evaluación de seguridad, revisión humana y métricas de costo, calidad y confiabilidad.

#### Aplicación en una organización

Una empresa que evalúa un agente para soporte de sistemas puede diseñar una prueba interna inspirada en estos enfoques. Puede incluir la corrección de errores de una aplicación, la configuración de un entorno de prueba y la resolución de incidentes mediante terminal. Además del éxito técnico, debe verificar que el agente respete permisos, no exponga información confidencial, deje registros auditables y solicite aprobación antes de realizar cambios irreversibles.
